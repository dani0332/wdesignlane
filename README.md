# Web Design Lane — static site

A rebuild of webdesignlane.com as a static site, generated by a small
zero-dependency Node script.

The live site is hand-written PHP behind Cloudflare, serving extensionless URLs
via `mod_rewrite`. This rebuild produces plain HTML files that reproduce those
same URLs, so it can replace the PHP site without breaking existing links or
rankings.

---

## Requirements

- **Node 18+** (developed on 24.19.0)
- Nothing else. No `package.json`, no `npm install`, no build dependencies.

---

## Quick start

```bash
# build into dist/
node build.mjs

# build and serve on http://localhost:4173
node build.mjs --serve

# build, serve, and show the palette switcher
node build.mjs --preview --serve
```

---

## How it works

There is no framework. Pages are JavaScript modules that export an HTML string.
`build.mjs` imports them, writes the result to `dist/`, and copies `assets/`
across unchanged.

```
src/pages/*.mjs          each exports a finished HTML string
        │                (built by calling page() from layout.mjs)
        ▼
build.mjs                imports every page, post-processes, writes files
        │
        ▼
dist/                    53 .html files + assets + .htaccess + sitemap
```

### The page shell

Individual page files never emit `<html>`, a header, or a footer. They build
only their **body**, then hand it to `page()`:

```js
export default page({
  slug: 'about.html',
  title: 'About Our Creative Digital Agency | Web Design Lane',
  description: '...',
  body,                      // just the <section> markup
});
```

`page()` (in `src/layout.mjs`) wraps that in the document shell and injects
`header(slug)` and `footer()` around it. That is why no page file imports
`footer` — there is exactly one place a footer is emitted, so all 53 pages are
guaranteed identical and cannot drift.

### Post-processing in `build.mjs`

After a page is rendered, the build applies two transforms:

1. **Theme** — rewrites `data-theme="signal"` if `--theme=` was passed.
2. **Link canonicalisation** — rewrites internal links to be extensionless and
   root-relative:

   | Authored | Emitted |
   | --- | --- |
   | `href="about.html"` | `href="/about"` |
   | `href="index.html"` | `href="/"` |
   | `src="assets/js/site.js"` | `src="/assets/js/site.js"` |

   Files on disk stay flat (`about.html`), and the server rewrites `/about` →
   `about.html`. Links are rewritten here so that internal clicks land on the
   final URL directly instead of eating the `.html` → extensionless 301.

### Placeholder pages

`build.mjs` walks the nav tree and footer columns, and for every link with no
corresponding page it generates a placeholder. This guarantees **no internal
link ever 404s**. All 53 nav and footer links now resolve to real pages, so the
build currently emits **0 placeholders** — the mechanism stays in place so a new
nav entry never ships as a 404.

## Project structure

```
build.mjs                 the generator + dev server
src/
  layout.mjs              page shell, header, footer, section components
  data/
    site.mjs              company details, nav tree, footer columns
    services.mjs          content for the service pages (barrel + 4 inline)
    services/             design.mjs, development.mjs, creative.mjs
    industries.mjs        content for the 14 industry pages
    locations.mjs         content for the 5 location pages
  pages/
    home.mjs              \
    about.mjs              | one module per real page
    contact.mjs           /
    legal.mjs             privacy policy + terms, one renderer for both
    service.mjs           shared template, renders every services.mjs entry
    industry.mjs          shared template, renders every industries.mjs entry
    location.mjs          shared template, renders every locations.mjs entry
assets/
  css/theme.css           ALL colour tokens — the only file a retheme touches
  css/base.css            layout and components (no hardcoded colours)
  js/site.js              nav dropdowns, mobile menu, palette switcher
  img/                    180 images
deploy/
  .htaccess               Apache config (auto-copied into dist/)
  nginx.conf              nginx server block (NOT copied — goes in /etc/nginx)
dist/                     BUILD OUTPUT — deleted and regenerated every build
```

> **Never edit anything in `dist/`.** The build starts with
> `fs.rmSync(dist, { recursive: true, force: true })`. Changes there are lost on
> the next build.

## Common tasks

### Change a footer link, phone number, or nav item

`src/data/site.mjs` → `company`, `nav`, `footerColumns`, `legalLinks`.
Rebuild; all 53 pages update together.

### Change the colour scheme

`assets/css/theme.css`. Every palette colour resolves to a token there.

One exception: `base.css` contains 13 literal `#fff` values — white text and
icons sitting on dark surfaces (primary buttons, the dark band, the footer, the
CTA panel). They are intentionally *not* tokenised, because they should stay
white in all three palettes. If you ever build a light-on-light or inverted
theme, those are the 13 places to revisit:

```bash
grep -n '#fff' assets/css/base.css
```

Three palettes ship with it:

| Theme | Primary | Notes |
| --- | --- | --- |
| `signal` *(default)* | `#fe6563` coral | Matches the current live site |
| `ember` | `#e2564b` terracotta | Warmer, amber accent |
| `harbor` | `#3b4ee0` indigo | Coral demoted to an accent |

```bash
node build.mjs --preview --serve     # compare them with the on-page switcher
node build.mjs --theme=ember         # bake one in for production
```

### Add a new service page

Add an entry to the `services` array in `src/data/services.mjs`. It is rendered
by the shared template in `src/pages/service.mjs` — no new code needed. If the
slug already appears in the nav, the placeholder is replaced automatically.

That array is assembled from four sources: four entries kept inline in
`services.mjs`, plus `services/design.mjs`, `services/development.mjs` and
`services/creative.mjs`. They are all the same shape — the split exists only to
keep any one file readable. Add your entry to whichever group it belongs to.

### Add an industry or location page

Same pattern, different data file: `src/data/industries.mjs` (rendered by
`src/pages/industry.mjs`) or `src/data/locations.mjs` (rendered by
`src/pages/location.mjs`). Industry entries carry a `dir` naming their folder
under `assets/img/industries/`. Location entries name their image paths
explicitly, because `assets/img/city/` is not uniform — only `banner-img` and
`s9bg` exist for every city.

### Add a one-off page

Create `src/pages/foo.mjs` exporting `page({...})`, then register it in
`build.mjs`:

```js
pages.set('foo.html', (await import('./src/pages/foo.mjs')).default);
```

## Build flags

| Flag | Effect |
| --- | --- |
| *(none)* | Build to `dist/` with the `signal` theme |
| `--theme=<name>` | `signal` \| `ember` \| `harbor` |
| `--serve` | Start a dev server after building |
| `--port=<n>` | Dev server port (default `4173`) |
| `--preview` | Add the floating palette switcher. **Never for production.** |

The dev server reproduces the `.htaccess` rules — `.html` → 301, trailing-slash
stripping, and real 404 status — so local behaviour matches production.

## Deployment

The build writes `sitemap.xml`, `robots.txt`, a themed `404.html`, and
`.htaccess` into `dist/`.

### Apache

1. `node build.mjs`
2. Upload the **contents** of `dist/` to the web root. Check your client is not
   skipping dotfiles — many hide `.htaccess` by default.
3. Ensure `AllowOverride All` is set for that directory, or `.htaccess` is
   silently ignored.
4. Verify: `curl -sI https://www.webdesignlane.com/about.html` → `301`
5. Purge the Cloudflare cache.

### nginx

1. Copy `deploy/nginx.conf` to `/etc/nginx/sites-available/webdesignlane`
2. Set `root` to the deployed `dist/` path and fill in the `ssl_certificate`
   lines
3. Symlink into `sites-enabled/`
4. `sudo nginx -t` — always; a bad config means no reload happens
5. `sudo systemctl reload nginx`

### Note on Cloudflare

The HTTPS redirect uses `X-Forwarded-Proto`, not `%{HTTPS}`, to avoid a redirect
loop behind the proxy. Cloudflare's own "Always Use HTTPS" overlaps with this —
enable one, not both.

## Known gaps

- **The contact form has no backend.** A static build cannot accept a POST. It
  currently intercepts submit and tells the visitor to call or email rather than
  silently dropping enquiries. Wire it to Formspree, Netlify Forms, or an
  endpoint before launch.
- **Assets are not content-hashed.** The cache rules in `.htaccess` target
  hashed filenames (`base.a3f9c1.css`), so the long-cache block for CSS/JS
  currently matches nothing. This is deliberate: caching unhashed assets is how
  a retheme silently fails to reach returning visitors. Implement hashing before
  enabling it.
- **`.htaccess` is untested against real Apache.** Its logic is verified by the
  dev server, which reproduces the same rules, but the Apache syntax itself has
  not been run. Check step 4 above on first deploy.

## Notes on the source site

Two issues found while rebuilding, which affect the live PHP site and are worth
fixing there too:

- **Soft 404s.** Missing URLs return HTTP `200` with the 404 page rendered, so
  search engines index them as real pages. This build returns a true `404`.
- **Stale `robots.txt`.** The live one declares a WordPress install at `/blog/`
  with `wp-admin` rules and links a `post-sitemap.xml` that 404s. There is no
  WordPress there any more.
